The key function is the keystone, so it ships by itself

Phase one is one task. Not because it is large, but because every later task hard-codes an assumption about what a key covers, and a key function written twice is the most expensive rework available here. It also has to be the piece with tests before anything depends on it.

Phase two is three tasks wide only because BC-1 defined the shape they all build against. Attempting the read path and the client in parallel before the key exists is how two components end up disagreeing about what they are keyed on.

What would make this a failure

Stated up front so the answer is not negotiated later. A hit rate below 40% on merge builds means the key function is wrong and the project has not delivered, even if every task is closed. A single verified poisoned entry is a stop-work condition, not a bug to triage.

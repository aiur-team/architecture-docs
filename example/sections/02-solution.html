The cache is easy. Deciding what a cache key covers is the whole problem.

A remote cache is a hash map in front of an object store, and that part is a week of work. The question that decides whether it can be trusted is narrower and harder: what counts as an input? Miss one, and the cache returns a stale artifact that compiles, passes, and is wrong.

Sound

Declared inputs

Source files, the toolchain version, the flags. Hashable and complete.

Partial

Ambient inputs

Environment variables and locale. Enumerable, but only if you look.

Unsound

Undeclared reads

A build that reads the clock or the network cannot be cached at all.

The key is a hash of everything the build is allowed to read

A cache entry is keyed by a digest over the ordered set of declared inputs: the content of every source file, the resolved toolchain version, the compiler flags, and the target platform. The key is not the command line. Two invocations that differ only in argument order must produce the same key, or the hit rate collapses without anybody noticing.

Entries are immutable. A second write to an existing key is compared and dropped, never overwritten — so a poisoned entry cannot replace a good one, and a mismatch is a loud signal that some input is not in the key.

Including every environment variable is the mistake that looks safest. It is technically correct and makes the cache useless, because CI_JOB_ID changes on every run and so does the key. An allow-list is the only workable answer, and it must be reviewed rather than guessed.

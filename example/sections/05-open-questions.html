Open questions

These are decisions, not research gaps. Each one has a cost that is not the author's to accept, and each is written so that a reader can answer it without reading the rest of the document.

1

May a developer machine write to the cache?

Allowing it roughly doubles the hit rate on the first build after a branch switch, because developers compile things CI has not reached yet. It also means the trusted store accepts bytes from an environment nobody attests to. Assumed answer: CI only, because a poisoned entry is unrecoverable in a way a slow build is not. Reversing this is a one-line policy change; reversing a poisoning incident is not.

2

What is the storage budget?

Eviction scoring is meaningless without a ceiling. At the measured artifact size and merge rate, an unbounded store grows by roughly 40 GB a week. The band design in Architecture assumes a fixed budget with pressure-driven eviction; a policy of "keep everything for 90 days" is a different design and a larger one.

3

Can one key span platforms?

If the target platform is in the digest, an arm64 laptop never reuses an x86 CI artifact, and the developer-facing benefit largely disappears. If it is not in the digest, the cache will eventually serve the wrong binary. Unresolved. The safe reading is to include the platform and accept the lower hit rate, but this has not been measured against real builds and the measurement is cheap.

4

Is a cache miss observable enough to debug?

A miss and a hit are indistinguishable in the build log today, which means a key regression looks exactly like a slow week. Nothing in the plan surfaces why a key missed. This is not a blocker, but it is the first thing anybody will ask for once phase two is live.

What is deliberately not being built

  • Distributed execution. A cache and a scheduler are different products. Reusing outputs does not require moving the work.
  • Cache warming. Predicting the next build's inputs is a research problem for a saving that eviction scoring mostly already delivers.
  • A UI. The hit rate and the uploaded-never-read count belong on an existing dashboard. A new web application is not warranted by two metrics.

An open-questions section earns its place only if the questions are real. If everything in it has an obvious answer, delete the section rather than padding it — and if the document has no genuine unknowns, say that in one line instead.

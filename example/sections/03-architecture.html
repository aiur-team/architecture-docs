Reads are open, writes are proved

The two paths have almost nothing in common, and merging them is the design error to avoid. A read is the hot path: it happens thousands of times a build, it must be fast, and the worst case of serving it to the wrong person is disclosure of a build artifact. A write is rare, and the worst case is a poisoned entry that every future build trusts.

Read path

Redirect, never proxy

The service answers with a short-lived signed URL and gets out of the way. Bytes never traverse the application, so throughput is the object store's problem rather than ours.

Write path

Only from a verified builder

A write carries a workload identity token that names the repository and the commit. A developer laptop may read everything and write nothing.

Entries age out by value, not by date

A fixed time-to-live throws away the entries worth keeping. The base image layer that every build reads is old and hot; a branch build's output is new and will never be read again. Eviction is scored on last access, not on age.

The middle band is the one that matters. An entry uploaded and never read is the signature of a key that is too specific — it means some volatile input crept into the digest. A rising count in that band is a bug report about the key function, not a capacity problem, and the dashboard should say so.

AWhy not just use the build tool's own remote cache?

Two reasons, and the first is not the interesting one. The build tools in use here disagree about key derivation, so a shared store behind them would hold two incompatible namespaces.

The real reason is that their write paths trust the client. Any developer who can read the cache can write to it, which is acceptable inside one team and not acceptable once CI trusts the result. The write-side identity check is the part we cannot delegate.

BWhat happens when the cache is down?

Builds get slower and nothing fails. The client treats every cache error — unreachable, slow, malformed — as a miss, and a miss is just a normal build.

This must be load-tested rather than assumed. The failure that actually happens is not an outage but a cache that answers in 30 seconds, and a client without a short timeout turns a degraded cache into a broken build.
